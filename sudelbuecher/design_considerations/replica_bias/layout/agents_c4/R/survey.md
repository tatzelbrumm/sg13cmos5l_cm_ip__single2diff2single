# Survey R: row-closing cells (fill / decap / endcap / tap) and 3.3 V logic / TG / switch / level-shifter cells

Claude, agent R, 2026-11-08 (cloud session C4). Read only: nothing in the design was changed, no external script was run, nothing pushed.
[M] = measured by me (klayout.db on the GDS, or a text read of a file), [D] = stated in a document or commit message (cited), [R] = my reasoning.
Previews: `previews/<name>.png` (device layers + Metal1/2, dashed = prBoundary 189/4). Short names below are the PNG names.

## 1. Headline findings

1. **There is no endcap and no tap cell, in any PDK library.** [D] `libs.tech/librelane/sg13cmos5l_stdcell/config.tcl`: "There are no endcap and welltie cells in ihp-sg13cmos5l thus set to undefined to skip insertion"; `FP_TAPCELL_DIST 0` ("No tap cells") in `libs.tech/librelane/config.tcl`. [M] The reason is visible in the GDS: **all 84 lv cells (and the 4 hv cells I could see) carry their own full-width Activ tie rails**: p+ tie to VSS on the bottom edge, n+ tie in the NWell to VDD on the top edge, contacts every 0.48 um. A row of std cells is therefore already "two tie strips between which the logic sits", exactly like your switch row; the PDK never closes the row ends.
2. **A thick-oxide (3.3 V) standard-cell library exists, but is not in our local PDK checkout.** `/foss/pdks/IHP-Open-PDK` is checked out detached at `df4c5054` (2026-10-14) without it. Its **`dev` ref (tip `3bccbc7b`, 2026-11-04) contains `ihp-sg13cmos5l/libs.ref/sg13cmos5l_stdcell_hv`** (symlinks into `ihp-sg13g2/libs.ref/sg13g2_stdcell_hv`) [M, `git ls-tree`, names only]. The blobs are not in the local partial clone (`blob:none`), so I could not read or render them: reading needs a network fetch into `/foss/pdks/.git`, which I did not do (outside the brief). What the tree and commit messages say:
   - The cell names (from `sch/qucs-s/sg13g2_hv_*.sch`, [M]) mirror the 84 lv cells: **`sg13g2_hv_fill_1/2/4/8`, `sg13g2_hv_decap_4/8`, `sg13g2_hv_antennanp`, `sg13g2_hv_tiehi/tielo`**, inv/nand/nor/and/or/mux2/ebufn/einvn ..., **no endcap or tap cell**, no transmission gate, no level shifter.
   - [D] commit `0ea7e4c5` (2026-08-17, Koen Van Caekenberghe): "All 84 cells of sg13g2_stdcell rebuilt on sg13_hv_nmos / sg13_hv_pmos ... L 130 nm -> 450 nm, PMOS width x 2.40 ... 17-track 7.14 um rows, CoreSiteHV 0.48 um site, DRC clean of all cell rules and LVS clean per cell under the PDK KLayout decks". Commit `301b36d6` (2026-08-18): "all 84 cells drawn ... LVS 84/84, KLayout clean on both DRC arrays, Magic zero NW.*".
   - [D] commit `865ae09e`: wells rebuilt "lateral overhang 0.24 -> 0.62 um so the outermost cell of a row is enclosure-clean without a neighbour"; "Magic's SG13G2 tech has no DigiBnd concept (issue #1107) and applies the analog N-well rules unconditionally". This is about row ends and Magic DRC and matters for you.
   - [M] The only hv cells I could measure are 4 of them, embedded in `rcyaon/bidir-level-shifter` `gds/slot_1.gds` (section 3). Their sizes agree with the commit text (row 7.14 um, NWell overhang 0.62 um).
3. **The lv decap/fill cells cannot sit across your 3.3 V rails** [R]: `sg13cmos5l_decap_4/8` are lv MOS capacitors (`sg13_lv_nmos` 0.42u/1u and `sg13_lv_pmos` 1u/1u, [D] `libs.ref/sg13cmos5l_stdcell/spice/sg13cmos5l_stdcell.spice`), characterized to 1.5 V. `fill_*` have no gate at all [M] (poly dummy only, not over Activ), so they are only well + ties.
4. The DRC deck has a rule family for dense hv rows, keyed on the `DigiBnd` marker (16/0), see section 4.

## 3. What the PDK says about endcaps, taps, fill, ties (documents and deck)

- [D] No endcap / tap cells: `libs.tech/librelane/sg13cmos5l_stdcell/config.tcl` (comment quoted above; `WELLTAP_CELL` / `ENDCAP_CELL` left unset); `libs.tech/librelane/config.tcl` `FP_TAPCELL_DIST 0`. Fill / decap: same `sg13cmos5l_stdcell/config.tcl`, `FILL_CELLS "sg13cmos5l_fill_1 sg13cmos5l_fill_2"`, `DECAP_CELLS "sg13cmos5l_decap_*"`, `DIODE_CELL sg13cmos5l_antennanp`, `CELL_PAD_EXCLUDE "...fill_* ...decap_*"`. Site: `CoreSite` 0.48 x 3.78 (`sg13cmos5l_stdcell.lef`).
- [D] `libs.doc/doc/SG13CMOS5L_os_layout_rules.pdf` (Rev 0.1, 2025-12-08): 5.1 NWell notes, p. 18: "Substrate ties for internal logic are required due to p-silicon substrate". 7.2.1 p. 54-55 (output buffers): "Place guard rings (VSS, VDD ties) around any NMOS and PMOS devices, which are directly tied to a pad. Double guard rings (N-Well isolator and P+ isolator) ... between n-channel and p-channel output buffers ... between output buffers and internal circuit area." 7.2.2: **LU.a/LU.b** max 20 um from P+Activ in NWell / N+Activ in PWell to a tie; **LU.c, c1, d, d1** max 6 um tie extension beyond Cont. "Latch-up rules are not checked by default." 8.1 p. 58: **"DigiBnd ... must be used when using IHP's standard digital libraries"**; inside it NW.c1 0.31, NW.d1 0.31, NW.e1 0.24, NW.f1 0.24, Cnt.c 0.05 (analog values for hv: NW.c1 0.62, NW.d1 0.62, NW.e1 0.62, NW.f1 0.62, Cnt.c 0.07).
- [M] Deck: `libs.tech/klayout/tech/drc/rule_decks/sg13cmos5l_maximal.drc` has LU.a, LU.c, LU.c1, LU.d, LU.d1 (under `$latchUpRules`, default true) and `NW.c1.dig`, `NW.d1.dig`, `NW.e1.dig`, `NW.f1.dig`, `Cnt.c.Digi`; `rule_decks/feol/5_1_nwell.drc` has `NW.f1` / `NW.f1.digibnd`, `feol/7_2_latchup.drc` has LU.b. No rule asks for endcaps, tap cells or fill cells.
- [M] Dummy fill (Activ / GatPoly / Metal:filler, AFil.*, GFil.*, M*Fil.*) is done by script, not by cells: PDK `tech/scripts/filler.py`; the harness does it at chip level (`make fill`, README step 11), so a slot does not fill its own area.
- [M] PDK PCells: `guard_ring` (types `nwell`, `psub`, `guard_ring_code.py:288`), `ptap1`, `ntap1` (min 0.78 um), and the `guardRingType` option of `pmosHV` (nwell) / `nmosHV` (psub). I did not instantiate them.
